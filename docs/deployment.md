# Deployment and recovery

## Ownership and ingress

The Worker `daymark`, its D1 database `daymark`, and the Custom Domain `daymark.lasers.app` belong to this application. `wrangler.jsonc` is the deployment configuration. Direct workers.dev and version preview URLs are disabled. Every static request goes through the Worker. The production configuration sets `ACCESS_REQUIRED` to `false` so the app shell and native sign-in are public; admin authorization remains mandatory.

Cloudflare Access applications protect the specific `/admin` and `/api/admin` paths with owner-only policies. The whole hostname has no blanket Access application after the public-local release procedure below. The admin audience is separate and remains mandatory in the Worker. The Worker verifies the signed Access JWT's issuer, audience, and expiry when the platform context is unavailable. Static Assets routing does not propagate the Access context; see [Cloudflare's integration documentation](https://developers.cloudflare.com/workers/configuration/cloudflare-access/).

Native app sessions use Better Auth, secure HttpOnly cookies in production, database-backed sessions, password hashing, and database-backed authentication rate limiting. Rate limiting is disabled only on the HTTP localhost development configuration. Server queries scope all operations to the native account, and sync requires the account ID the browser believes is signed in. Account deactivation revokes sessions. Cross-origin mutations are rejected. Admin mutations require both the owner Access identity and a native owner account.

## Secrets and provisioning

Supply `AUTH_SECRET` (at least 32 random bytes encoded as a string) and `OWNER_EMAIL` through Wrangler secrets, never tracked variables. Keep a protected, structured recovery copy in your automation credential store. Secret rotation invalidates app sessions; retain the D1 database and users when rotating. Cloudflare API credentials belong to the release environment or operator machine, outside the application.

For a new installation, create the D1 database, set its identifier in Wrangler, create the owner-only Access applications for `/admin` and `/api/admin` and their exact allow policies, then set issuer and admin audience variables before attaching the Custom Domain. Provision secrets with `npx wrangler secret bulk <protected-json-file>` using an object whose keys are `AUTH_SECRET` and `OWNER_EMAIL`. Never print or commit that file.

```sh
npm ci
npx playwright install chromium
npm run verify
npx wrangler d1 migrations apply daymark --remote
npx wrangler deploy
```

These commands provision or recover an installation under explicit operator approval. Apply schema migrations before deploying code that requires them, after reviewing the entire pending set. The dry-run output is kept outside the static asset directory. Deploy clean, tested source and retain Wrangler's version ID in the release evidence. Do not attach a public test hostname to bypass Access. Routine releases use the automated flow below.

## Automated production releases

The Verify and deploy workflow verifies pull requests and pushes. A successful push to protected `main`, or a manual workflow dispatch on protected `main`, automatically starts the production release. It is restricted to `j-256/daymark`. The `production` environment has no required reviewer; routine releases need no browser approval. Use `gh workflow run ci.yml --ref main` to request verification and deployment from the terminal.

Configure the `production` environment's Actions secret `CLOUDFLARE_API_TOKEN` and Actions variable `CLOUDFLARE_ACCOUNT_ID`. The token needs account-scoped Workers Scripts Write and D1 Edit, also called D1 Write in the API. Scope it to the owning account. The release uploads a Worker version and activates that exact version, leaving existing routes and the Custom Domain unchanged. It does not require Zone Workers Routes Write. Initial provisioning and intentional route changes still require the operator's appropriate zone permission. See [Workers authorization](https://developers.cloudflare.com/workers/authorization/workers/) and [GitHub Actions deployment](https://developers.cloudflare.com/workers/ci-cd/external-cicd/github-actions/).

The verification job runs the complete verification command, then hashes the compiled Worker, static assets including hidden exclusion files, configuration, and migration inputs into an artifact receipt bound to its source revision. The release job downloads that run's artifact and checks every digest and the exact file set before production mutation. It uploads the compiled entry point with `--no-bundle`, uses the verified asset directory, and sets the existing `BUILD_ID` variable to the source revision. Application secrets remain in Cloudflare. Production credentials are available only to the release step, and pull request jobs receive none.

Main workflows and production jobs are serialized without automatically cancelling an active release. A newer push can replace a pending run; GitHub concurrency does not promise a FIFO release queue. Source checks before migration writes, upload, and activation reject a revision that has been superseded on protected `main`. Do not manually cancel a release during database writes without inspecting its resulting state.

The migration preflight reads only migration filenames and requires a contiguous prefix of the reviewed manifest. Unknown history or pending manual migrations stop the release. Pending automatic migrations require a recorded Time Travel bookmark, successful migration application, and a complete applied-history readback before upload. An empty pending set performs no D1 writes or bookmark work. Migration review and recovery requirements are documented in [Database migrations](migrations.md).

Wrangler's structured upload record must identify exactly one version of `daymark`; activation uses that version ID explicitly. The release checks the active deployment, public shell, exact `/api/config` build revision, closed registration and rejected public signup, anonymous rejection by sync and health endpoints, and owner Access redirects on administration paths. Read-only checks allow a bounded propagation window. These probes do not establish authenticated database health or account synchronization; complete the account acceptance checks below when account behavior changes.

The Actions job summary and release-report artifact record the source revision, stage, timings, pending migration names, recovery bookmark when applicable, and uploaded Worker version. Smoke diagnostics include request IDs and statuses without account data. Release reports expire after seven days; verified build artifacts expire after one day. Download any evidence needed for a longer recovery record. D1's recovery retention is independent of GitHub artifact retention. No production SQL export is uploaded to Actions.

On a failed migration, stop and inspect applied history before retrying; earlier successful migrations can remain applied. On upload or activation failure, inspect provider versions and the active deployment before retrying an uncertain write. A failed smoke check retains the activated version in its report and does not trigger an automatic rollback or database restore. Prefer a compatible forward fix. Any database restore is a separately approved operation because it overwrites later writes. For an approved code rollback, select a version compatible with the deployed schema and preserve the recorded recovery information.

The build removes Finder metadata before generating the offline shell. The release configuration check rejects unexpected files in the static artifact, and `.assetsignore` excludes root and nested `.DS_Store` files even if Finder creates them after verification. Cloudflare documents this exclusion format in [Ignoring assets](https://developers.cloudflare.com/workers/static-assets/binding/#ignoring-assets), checked on 2026-10-24.

After deploying, read back the hostname, Worker, D1 binding, admin Access applications and policies, and disabled provider URLs. An anonymous request to `/` must serve the app, `/api/sync` must return a native 401, and admin paths must retain owner-only Access protection. Cross-origin mutations must fail. An Access redirect proves ingress protection; it does not prove authenticated application health. Complete an anonymous local tracker write, offline reload, backup restore, invited-account login, and second-device merge. Confirm local history never appears in the account unless explicitly imported.

## Public local release and Access transition

Integration into protected `main` triggers release verification and deployment. Provider Access policy changes remain separate operator actions. When performing a public-local Access transition, release the compatible build before removing the blanket gate:

1. Verify the clean integration branch and deploy it with `ACCESS_REQUIRED=false`; retain owner-only admin Access applications and the separate admin audience
2. Verify that the public signup route rejects registration even when an older `app_settings` record says `open`, and that the owner can still create an invited account
3. Inventory Access applications and policies; remove only the exact whole-host application for `daymark.lasers.app`, preserving `/admin`, `/admin/*`, `/api/admin`, and `/api/admin/*` coverage and any other hostname's policies
4. From a fresh browser with no Access or native cookies, verify `/` loads, local logging and backups work, and `/api/sync` remains unauthorized; verify non-owner admin access is denied
5. Sign in as an invited non-owner, test synchronization and sign-out, then verify local/account histories remain isolated

Use Cloudflare Fleet to inspect deployed Worker/domain state and any purpose-built Access tooling available to the operator before falling back to Cloudflare's Access management interface. Do not add a whole-host bypass policy or open public registration. The server always reports registration closed and rejects attempts to enable it. Owner bootstrap and manual account creation remain available through protected admin routes.

To restore the outer gate, restore the exact reviewed whole-host Access policy and set `ACCESS_REQUIRED=true` in a separately reviewed recovery deployment. Preserve D1 and browser data. Do not remove the admin policies as part of either transition.

## Synchronization and recovery

Each edit has a random ID and parent IDs identifying the versions the browser observed. The server atomically appends a bounded batch; identical retries are idempotent, ID collisions and missing or cross-record parents reject the whole batch. Pulls use an indexed, account-specific cursor. Conflicts keep every distinct concurrent head. Resolving a conflict creates an edit referencing all versions shown to the user.

IndexedDB commits precede successful UI updates. Only acknowledged operation IDs leave the pending queue. Failed network requests, expired sessions, Access redirects, and rejected batches preserve local work. For signed-in accounts, reconnect, focus, visible-page timers, and new edits trigger sync. The anonymous local workspace creates no sync engine, timer, or account API probes. Background Sync is not required: keep a browser tab open or reopen Daymark to resume. The service worker precaches the complete application shell, serves public navigation from that cache, never caches API responses or protected admin navigation, and rejects redirects during installation. A first visit needs a connection. Browser-managed service-worker update checks can still use the network, and new releases download a complete updated shell. No analytics or external assets are required. Cache loss requires a new download while IndexedDB loss requires a backup restore.

Inventory metadata, independently keyed stock movements, and consumption snapshots on activity records share the same operation log and per-account backups. Inventory quantities are stored as integer thousandths of the named unit. Creating a supply with opening stock writes a metadata operation and a stock operation; refills and manual use each write one operation. Linked dose consumption is part of the activity operation, so it adds no separate server query or operation. Include stock changes in the D1 workload estimate.

Sync requests require `X-Daymark-Sync: 2`. Older cached clients receive `client_update_required` before uploading or downloading operations and retain their pending local history. The compatible client uses a separate per-account IndexedDB database so an already-open legacy tab cannot overwrite inventory snapshots. It imports missing operations from legacy storage before listing or syncing, retains their pending flags, and leaves the legacy database intact. Later edits from older tabs are imported through the shared account change notification or the next sync. Reopen the app online to download an updated shell, then reopen after the update is installed and let pending account operations sync. Do not clear browser storage to solve a client-version mismatch. Rolling back to code that does not understand inventory requires compatible code and data recovery together.

Use Settings to export a complete workspace JSON backup before browser maintenance. Imports validate the full causal graph, reject ID collisions and unsupported formats, and merge atomically. Another workspace requires explicit consent through "Import from another workspace"; imported operations in an account become pending sync edits, while imports into the local workspace stay local. Signing in never migrates local history automatically. Backups include inventory, stock, archived records, and conflict history; they omit credentials, sessions, and device appearance/layout preferences. For disaster recovery, export the remote D1 database with `npx wrangler d1 export daymark --remote --output <protected-backup.sql>`. Protect SQL exports as credential and activity data. D1 Time Travel retention depends on the account plan; verify its available bookmark before running a restore. Back up before migrations or restoration. Worker rollback does not roll back the database. Restore compatible code and database together and retest session and sync behavior. V1 does not automatically schedule exports.

## Diagnostics

API responses include `X-Request-ID`; failures return the same correlation ID. Worker logs record route class, status, duration, and safe reason codes. Sync writes also record batch size and D1 row metrics. Logs exclude operation values, notes, email addresses, cookies, and credentials. Use `npx wrangler tail daymark` or Cloudflare Workers Logs to correlate a failing request; match the request ID rather than copying activity contents into a ticket. Authentication logs from the auth library are disabled. Worker observability is enabled; configure retention in Cloudflare for the account's operational needs.

## Cloudflare Free-plan assessment

Official limits were checked on 2026-10-24. This application uses no Queues, Durable Objects, R2, paid identity provider, or paid email service. Successful testing on a Paid account does not establish Free-plan compatibility.

- [Workers limits](https://developers.cloudflare.com/workers/platform/limits/) allow 100,000 requests per day, 10 ms CPU per invocation, 128 MB memory, a 64 MiB uncompressed Worker, 20,000 static files, and 25 MiB per asset on Free. Worker-first serving invokes code for shell requests, so include those requests in the workload budget
- Native password hashing is deliberately expensive and can exceed the Free 10 ms CPU limit. Password creation, login, and resets require a plan with sufficient CPU allowance unless an actual Free-account measurement demonstrates otherwise. This is a compute risk inherent to the chosen password authentication path, not a request-volume issue. No weak-hash fallback is supported. A separately implemented external identity or passkey flow could avoid password hashing at the cost of another authentication design; it is not a v1 switch
- [D1 pricing](https://developers.cloudflare.com/d1/platform/pricing/) gives Free accounts 5 million rows read per day, 100,000 rows written per day, and 5 GB total storage. These quotas are shared with other databases in the account. Exceeding daily query limits stops server sync until midnight UTC; local edits stay queued. Index writes and authentication/session queries also count
- Anonymous local logging performs no D1 queries and has no server-side activity storage. Initial shell downloads and browser update checks still consume network requests; Worker-first routing includes those requests in the Worker budget. Invited accounts retain the authenticated polling and database costs described here
- A planning workload of 20 people logging 20 edits per day produces 400 operation rows per day. At an assumed 1 KiB per operation, activity payload grows by about 143 MiB per year before indexes and authentication data. This is a projection, not measured production usage. Device count, idle polling, note sizes, conflicts, and retries change query costs; inspect emitted D1 metrics instead of treating edit count as write count
- A local release dry run measured approximately 1.8 MiB of uncompressed Worker code and 330 KiB compressed; the main browser script was approximately 295 kB before compression. These are artifact measurements, not Free-account runtime CPU measurements
- Reproduce asset and Worker size measurements with `npm run build`, `npm run check:deploy`, and `du -sh dist .worker-dry-run`. Exercise authentication on the actual target plan and inspect CPU metrics before claiming Free compatibility. V1 has no causal-history compaction, so long-lived accounts eventually require a storage and client-memory strategy

A reorder can create an operation for each tracker in the displayed list when ranks need normalization. The browser persists the group atomically; server uploads use the same bounded batches as logging. Count each generated operation in D1 workload estimates rather than treating a reorder as a single row.

The deployed account may use Workers Paid for reliable native password authentication. GitHub Actions verification has no production credentials; the separate release job receives environment credentials only after verification of protected `main`. The local integration queue runs the same verification command before publishing approved changes; GitHub branch protection also requires the hosted `verify` check before merging. Release smoke checks add at most approximately fifty Worker requests per release under the bounded retry policy, including anonymous authentication rejection and Access-boundary probes. Count these with normal application traffic when estimating Free-plan request usage. Migration SQL has workload-dependent D1 costs and duration; local tests and a successful Worker dry run do not establish production D1 quota compatibility.
