# Database migrations

Store schema changes in numbered SQL files under `migrations/`. Every SQL file needs an entry in `migrations/manifest.json` containing its `name`, SHA-256 `sha256`, and reviewed `mode`: `automatic` or `manual`. Compute the digest with `shasum -a 256 migrations/<filename>.sql`. SQL filenames use a four-digit version followed by lowercase words and underscores, such as `0003_add_tracker_index.sql`. Versions must be unique and append after existing history.

Applied and merged migrations are immutable. Do not edit, rename, delete, or change the policy of an existing migration; add a new one instead. `npm run check:migrations` checks file coverage and digests and compares historical SQL and policies with `origin/main`. Use `-- --base <revision>` to select a different trusted base. GitHub verification selects the pull request base or the previous push revision. A changed digest in the manifest does not authorize changing historical SQL.

Start new migrations with `manual`. A reviewer may select `automatic` before the migration merges only when the change is compatible with the running Worker and older clients. Adding a nullable column or an index can qualify after reviewing the application's queries and workload. Renaming or removing fields, changing meanings or constraints, rebuilding tables, and transforming existing records need a staged operator plan. The policy records this review; a manifest entry does not prove SQL compatibility.

Use an expand-and-contract sequence for incompatible changes: introduce a compatible schema, release code that tolerates old and new representations, backfill deliberately, and remove obsolete structures in a separate approved operation. Account for offline clients and the application's sync protocol. Do not weaken constraints or clear browser storage to make a migration appear successful.

The API tests discover the complete migration chain. Migration tests exercise installation, upgrades preserving synthetic account and operation records, quoted semicolons, and failure rollback. Add representative existing-data fixtures when a new migration changes stored records or constraints. Fresh-schema success alone does not establish upgrade safety. Local D1 tests do not measure production migration duration or Free-plan resource usage.

Production automation accepts only a contiguous prefix of the known migration history and refuses pending manual migrations. Initial database provisioning is an operator action: apply the reviewed initial schema before enabling routine deployment. For an approved manual migration, inspect history, capture a recovery point, run `npx wrangler d1 migrations apply daymark --remote` from the reviewed source, and read back the result before retrying deployment. This command applies all pending SQL files, so review the entire pending set first.

Wrangler rolls back the failing migration, while previously successful migrations remain applied. A failed release must stop before uploading or activating new code. Never assume the entire migration set rolled back. Inspect the applied history and prefer a compatible forward fix. See [Cloudflare's migration command behavior](https://developers.cloudflare.com/d1/wrangler-commands/#d1-migrations-apply).

D1 Time Travel bookmarks identify a recovery point; they do not create a permanent backup. The retention window is seven days on Workers Free and thirty days on Workers Paid, verified on 2026-10-26 against [D1 limits](https://developers.cloudflare.com/d1/platform/limits/). Record a bookmark immediately before production migrations. A [Time Travel restore](https://developers.cloudflare.com/d1/reference/time-travel/) overwrites the database, cancels in-flight queries, and removes later writes from the restored state. Restore only as a separately approved recovery operation with an account-data reconciliation plan. Worker rollback does not restore D1. Keep any SQL exports in protected private storage, outside static assets and public CI artifacts.
